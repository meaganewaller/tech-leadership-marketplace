# Gemini CLI adapter

Gemini CLI doesn't load bare skill folders directly -- it loads
**extensions**: self-contained directories with a `gemini-extension.json`
manifest, from which it auto-discovers a bundled `skills/` directory and
loads any `SKILL.md` it finds. So the unit of distribution for Gemini is one
extension per plugin, generated from this marketplace's canonical content.

## Build and install

```bash
adapters/gemini/install.sh <plugin-name>
```

This builds `.gemini-extensions-build/<plugin-name>/` containing a generated
`gemini-extension.json` (name, version, description taken from the plugin's
own `plugin.json`, so they never drift out of sync) plus every skill the
plugin has, copied in unchanged. The script prints the install command:

```bash
gemini extensions install ./.gemini-extensions-build/<plugin-name>
```

For local development, where you want edits in this marketplace to show up
without reinstalling:

```bash
gemini extensions link ./.gemini-extensions-build/<plugin-name>
```

(Note `link` symlinks the *build output*, not this repo directly -- rerun
the install script after editing a skill, or point `link` at
`plugins/<plugin-name>` directly and hand-maintain a `gemini-extension.json`
there instead, if you prefer skipping the build step during development.)

## Why one extension per plugin, not one for the whole marketplace

A single combined extension would force an all-or-nothing install and a
single version number across unrelated plugins (PR review vs. debugging vs.
future 1:1-prep content). Per-plugin extensions let someone install just
`debug-session-tracker` without also getting everything else.

## Also relevant to Gemini

`gemini-extension.json` supports a `contextFileName` field for a shared
context file (Gemini's equivalent of AGENTS.md, loaded every session the
extension is active) and an `mcpServers` field for bundling MCP servers.
Neither is generated by this script since no current plugin needs them --
add them by hand to a specific extension's manifest if one does.
